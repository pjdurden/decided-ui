The spec API

One file declares every decision your interface is willing to delegate. It is TypeScript, so it is checked against your components.

This is a design reference for a package that is not built yet. Signatures may change before P1 ships. See the roadmap.

defineSpec

import { defineSpec, variant, presence, rank, intensity } from "@decided-ui/core"

export const spec = defineSpec({
  layout:    variant(...),
  hero:      variant(...),
  financing: presence(...),
  urgency:   intensity(...),
  panels:    rank(...),
})

export type Spec = typeof spec

Keys are slot names and are the ids you use in <Slot name="hero" />, in impressions, and in your analytics. Renaming one is a breaking change to your historical data, so name them for what they are rather than what they currently contain.

defineSpec returns a frozen object carrying a specVersion: a stable hash of every question and criterion. Change a criterion and the hash changes, which is what lets you segment measurements by spec revision instead of silently pooling results from two different questions.

variant(Component, options)

Chooses one of several versions of a component.

hero: variant(Hero, {
  question: "Which opening treatment fits this shopper?",
  default: "bigImage",
  options: {
    bigImage:   "Judges by look and brand feel, reads little detail",
    specTable:  "Opens with numbers and compares models on specifications",
    videoFirst: "Unfamiliar with the product and needs to see it in use",
  },
})
FieldType
questionstringrequired. Carries the full meaning; slot ids are never sent to the model.
optionsRecord<V, string>required. V is inferred from the component's own variant union, so a typo is a compile error.
defaultVrequired. Used whenever the gate fires or no answer arrives.
floornumberoptional per-slot confidence floor, overriding the global one.

A variant() slot does not have to render a component. If the value is consumed as a class name or a data attribute, you get whole-page layout switching for free, which is how the prototype produces four visibly different pages from one component tree.

// layout as a variant whose value becomes an attribute
<article data-layout={useDecision("layout")}>

presence(options)

Decides whether a block appears at all.

financing: presence({
  question: "Should a monthly instalment option be offered to this shopper?",
  default: false,
  when: {
    true:  "Budget constrained, and the item is a large one-off cost",
    false: "Buys outright, or the item is cheap enough that instalments are noise",
  },
})

when is optional but recommended: describing both sides sharpens the judgment considerably. The returned probability is compared against a threshold that defaults to 0.5.

Remember that the answer is a probability, not a boolean. A value near 0.5 means the model genuinely cannot tell, which is different from a confident no.

rank(items, options)

Orders a set of blocks by how important each is to this person.

panels: rank(["price", "proof", "specs", "shipping", "related"], {
  question: "How central is each of these to this shopper's decision?",
  levels: ["irrelevant", "minor", "useful", "important", "decisive"],
  defaults: { related: "minor" },      // per-item, falls back to the middle level
  max: 5,                              // structural cap
})

Each item becomes its own comparable Score question, and code sorts the results descending. Ties break by declaration order, so the ordering is total and stable: the same answers always produce the same page, and an item with no answer sits exactly where its declared default puts it rather than at the bottom.

Levels describe situations, not degrees. “Will not buy without reading what other owners said” discriminates. “Quite important” does not. Up to ten levels; use as many as you can describe distinctly and no more.

intensity(options)

Places one thing on a scale you describe.

urgency: intensity({
  question: "How strongly should limited availability be signalled?",
  levels: ["none", "soft", "urgent"],
  default: "none",
})

The model returns a float, the probability-weighted mean of the level indices. The assembler bands it to the nearest level, rounding half up and clamping to the range. You can read the raw float instead if you want something continuous, such as an opacity or a delay.

Overriding the assembler

The default policy is exported and composable, so overriding one rule does not mean rewriting the rest.

import { defaultPolicy, defineSpec } from "@decided-ui/core"

export const spec = defineSpec({ /* slots */ }, {
  policy: {
    ...defaultPolicy,
    confidenceFloor: 0.62,
    onGated: (slot, reason) => metrics.increment("ui.gated", { slot, reason }),
  },
})
OptionDefault
confidenceFloor0.55tune against your own data. It is a starting point, not a constant of nature.
presenceThreshold0.5above this, the block renders.
onGatednonecalled whenever a default is used instead of the model's answer.
timeoutMs5000on timeout every slot falls back to its default.

Rendering

import { Provider, Slot, useDecision, track } from "@decided-ui/react"

<Provider decision={decision}>
  <Slot name="hero" />              {/* renders the chosen Hero variant */}
  <Slot name="financing" />         {/* renders nothing if presence said no */}
  {useDecision("panels").map(p => <Slot key={p} name={p} />)}
</Provider>

<Slot> fires exactly one impression when it mounts and never on re-render. track("purchase", { value }) stamps the active decision id onto a conversion so it joins back to the variants that produced it. See measurement.
