Measurement

Two event types and one shared id are enough to ask which interface won. This is the capability generative UI does not have.

Why this is the whole point

If a model generates an interface, you can tell whether that session converted. You cannot tell whether the interface was why, because the thing it produced has no name and will never be produced again. There is nothing to aggregate.

A decided interface is a small set of named variants. Every impression is a row saying which variant a person saw. Every conversion is a row saying what they then did. Joining the two is an ordinary funnel question that Amplitude, PostHog and Mixpanel have answered for a decade.

The Tracker contract

interface Tracker {
  impression(e: {
    decisionId: string       // unique per decision
    specVersion: string      // hash of the spec that produced it
    slot: string             // "hero"
    variant: string          // "specTable"
    confidence: number       // 0 to 1
    gated: boolean           // true when the default was used instead
    gatedReason?: "low_confidence" | "no_answer" | "undeclared_option"
  }): void

  conversion(e: {
    decisionId: string
    event: string            // "purchase", "signup", whatever you count
    props?: Record<string, unknown>
  }): void

  identify?(userId: string): void
}

Four methods, one of them optional. An adapter for a provider you already use is an afternoon, and the Amplitude one ships first.

import { Provider } from "@decided-ui/react"
import { amplitudeTracker } from "@decided-ui/amplitude"

<Provider decision={decision} tracker={amplitudeTracker(amplitude)}>

Impression discipline

Exactly one impression per slot per decision, fired on mount, never on re-render. This sounds like a detail and it is actually the whole integrity of the numbers: a slot inside a component that re-renders on every keystroke will otherwise report a hundred impressions for one view, and every conversion rate you compute afterwards will be wrong in a way that looks plausible.

<Slot> handles this for you. If you render a decided variant by hand rather than through <Slot>, you own the deduplication, and the framework cannot help you.

Gated impressions still fire. When the gate fires, the impression records the default that actually rendered, with gated: true and the reason. You want those in the data: a slot that is gated forty per cent of the time has criteria that are not discriminating, and that is a finding about your spec, not noise to filter out.

Questions you can answer on day one

QuestionHow
Which hero converts better?conversion rate grouped by variant where slot = "hero"
Is the model beating a fixed default?compare gated: true impressions against gated: false for the same slot and variant
Is this slot worth the call?if every variant converts within noise of the others, delete the slot and ship the default
Did rewriting a criterion help?segment by specVersion, which changes when the criterion text does
Where is the model unsure?distribution of confidence per slot; a slot clustered near the floor needs better criteria

The second row is the one people forget to ask, and it is the honest one. The gate means a meaningful share of your traffic already sees the declared default, which gives you a control group you did not have to construct.

Closing the loop

The framework stops at emitting events. It does not store outcomes, run assignment, or tell you which variant won. That is deliberate: building those things means building an experimentation platform, and you already pay for one.

What you do with the numbers is the part that makes this a paradigm rather than a party trick:

  1. A variant loses consistently. Delete it. The spec shrinks and every future call gets cheaper.
  2. A slot never discriminates. Delete the slot. You were paying for a question with no answer.
  3. A slot is gated constantly. Rewrite the criteria as concrete situations rather than degrees, and watch specVersion change so you can measure whether it helped.
  4. A variant wins for one segment and loses for another. That is not a variant to delete, that is a criterion to sharpen.

None of these steps are automated, and none of them should be. They are design decisions informed by evidence, which is the thing the industry has been trying to get back to since personalisation became a black box.

Privacy

The state you send is whatever you choose to send. The spec is the contract for what is actually read, so it doubles as an auditable list of what leaves your servers. Send a summary rather than raw PII where you can: it is usually a better question anyway, because “comparing several models on price” discriminates and an email address does not.

Impressions carry no user data of their own beyond the decision id. Joining to a person happens in your analytics tool, under whatever identity model you already operate.
