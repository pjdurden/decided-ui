Versus generative UI

Generative UI is the more ambitious idea and, for a genuinely open-ended surface, the right one. If a user can ask for anything and the interface must be shaped to the request, no fixed set of variants will do.

For a product page, a dashboard, an onboarding flow or a pricing page, the set of good interfaces is small, known, and was designed by someone. Generating one per request pays seconds of latency and gives up validation, visual regression testing and measurement, to arrive somewhere a designer has already been.

The honest summary: generative UI trades latency and measurability for expressiveness. Decided UI takes that trade in the other direction, and most production surfaces want it in the other direction.

Versus A/B testing

An A/B test assigns randomly and measures. decided-ui assigns by judgment and measures. They answer different questions: a test asks “which variant is better on average”, this asks “which variant is better for this person”.

They compose well. Run a test to learn that the spec table hero wins overall, then encode when it does not in a criterion, then use the impression data to check the model actually finds those cases. If your variants do not differ by segment, you do not need this; you need to ship the winner and delete the loser.

Versus feature flags and rules engines

A rule is better than a model whenever you can write the rule. if (user.plan === "enterprise") is faster, free, deterministic and never wrong.

The case for a model is the long tail: the conditions you cannot enumerate, and free text you cannot pattern match. “Buying a leaving gift for a colleague and needs it before Friday” is not a flag you were going to write, and it is a real shopper with a real preference about what your page should emphasise.

Use both. Nothing stops you gating a slot behind a flag and letting the model choose within it. Rules for what you know, judgment for what you do not.

Versus a personalisation or recommendation engine

A learned personalisation system is better than this once you have the traffic and the labels to train it. It optimises directly against outcomes rather than against a sentence someone wrote.

Three situations favour a decided interface. You are starting cold and have no interaction history to learn from. You need the decision to be inspectable, because someone will ask why this user saw this page. Or the signal you are deciding on is language, which a collaborative filter cannot read at all.

These also compose: the impression and conversion stream this produces is exactly the labelled training data a learned model would need later. Scoring judgments once and letting code combine them is a reasonable on-ramp to classical ML, not a competitor to it.

When not to use this

  • You have one good interface. Ship it. Do not manufacture variants so a model has something to choose between.
  • The right answer is knowable from data you hold. Write the rule.
  • The surface is genuinely open-ended. Generate it.
  • You cannot describe the situations your variants are for. If you cannot write the criterion, the model cannot apply it, and you will get an expensive coin flip with a confidence score attached.
  • You will not look at the numbers. Without the measurement stage this is decoration with a bill.
