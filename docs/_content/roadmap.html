Roadmap

What exists, what is next, and what done means for each phase.

Nothing is installable today. P0 is a Python prototype that proved the loop and produced the numbers quoted across this site. The TypeScript packages are designed but unbuilt.

P0  Prototypedone

Python, server rendered. Four page layouts, twelve questions in one batched call to Jev, deterministic assembly, a confidence gate, and an explanation panel showing every question and its distribution.

Done means: a free-text shopper description typed on the spot produces a page no preset produces; the assembler's policy is unit tested with no network; and the latency figures are measured rather than estimated. All three hold.

P1  core and reactnext

@decided-ui/core: the four primitives, the question compiler, typed answers, and the default assembler policy. @decided-ui/react: provider, <Slot>, useDecision(), impression-on-mount.

Driven by a mock decider, so the entire phase runs with no API key, no network and no cost, and is fully unit testable.

Done means: npm install, define a spec, render a page whose variants change when the mock decider is handed different answers, and renaming a variant in a component breaks the build.

P2  the server adapterplanned

@decided-ui/next: route handler, App Router server action, key handling, and the answer cache keyed on the state fields the spec actually reads.

Done means: a Next.js app makes one real call per uncached visitor, the key never reaches the browser, and every failure mode named in architecture renders the default page rather than an error.

P3  measurementplanned

The Tracker interface in core and @decided-ui/amplitude. One impression per slot per decision, conversions stamped with the active decision id.

Done means: a funnel in Amplitude answers “which variant of this slot converted better” with no custom instrumentation, and a re-rendering component still reports exactly one impression.

P4  the example and the docsplanned

The storefront prototype ported to React as a real example app, and these pages become documentation for something that exists rather than a design.

Done means: clone the example, add a key, and have a decided page running in under ten minutes.

Deliberately not planned

  • Assignment, storage and reporting. That is an experimentation platform. Adapters, not a product.
  • A component library. You write the components. That is the point.
  • Automatic criteria rewriting. Tempting and wrong. A model proposing its own questions removes the one part a human should own.
  • Client-side deciding. The key belongs on a server, and there is no version of this where shipping it to the browser is acceptable.

Open questions

Recorded honestly, because they are not resolved.

  • Streaming. Half a second is fine for a server-rendered page and awkward for a client transition. Whether to render defaults immediately and swap on arrival, or block, is unresolved and probably belongs to the app rather than the framework.
  • Spec size. Twelve questions is comfortable. Nobody has established where the useful ceiling is, or whether a large spec degrades individual answers.
  • Criteria authoring. The real labour, and currently unsupported. A linter that flags criteria describing degrees rather than situations would help more than any runtime feature.
  • The 300 ms target. Missed by 1.6x to 2.4x in the only measurements taken. Whether that is the network, the region, or the shape of a twelve-question request is not yet known.
