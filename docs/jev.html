Decision engine

Jev, the decision engine

Why a System One model rather than an LLM, and exactly what comes back.

decided-ui delegates every judgment to Jev, TypeSafe’s System One model. Jev does not write text. You give it state and a set of typed questions, and it returns typed answers with calibrated probabilities. That property is what the whole framework is built on.

Why not just call an LLM

You could ask GPT or Claude “which hero should I show this shopper” and parse the reply. Four things go wrong, and each of them is load-bearing here.

An LLMJev
Returnstext you must parse, or JSON you must validatea typed answer, by construction
Uncertaintya number it wrote, uncorrelated with being righta distribution over the options you declared
Twelve questionstwelve calls, or one long prompt that degradesone call, answered in parallel
Latencysecondssub-second

The second row is the one that matters most. The confidence gate is the mechanism that keeps a wrong model from producing a bad page, and it only works if the number it gates on means something. A self-reported confidence from a text model does not.

How the four primitives map

decided-ui’s primitives are a thin, opinionated layer over Jev’s three question types.

decided-uiJev typeNotes
variant()Choicecriteria is a map of option name to description. Up to 255 options, though a UI slot with more than a handful is a design smell.
presence()Noulreturns the probability of yes. Optional true and false descriptions sharpen it.
rank()Score, one per itemeach item gets its own comparable question, and code sorts the results.
intensity()Scorecriteria is an ordered list of level descriptions, up to ten.

What actually goes over the wire

One POST to https://api.typesafe.ai/v1/systemone with a bearer token, carrying your state and every question at once.

{
  "model": "jev-latest",
  "state": { "shopper": { "summary": "Comparing four models on a spreadsheet." } },
  "questions": {
    "variant_hero": {
      "type": "choice",
      "instructions": "Which opening treatment fits this shopper?",
      "criteria": {
        "bigImage":  "Judges by look and brand feel, reads little detail",
        "specTable": "Opens with numbers and compares models on specifications"
      }
    },
    "presence_financing": {
      "type": "noul",
      "instructions": "Should a monthly instalment option be offered?"
    },
    "intensity_urgency": {
      "type": "score",
      "instructions": "How strongly should limited stock be signalled?",
      "criteria": ["none", "soft", "urgent"]
    }
  }
}

And what comes back

{
  "model": "jev-1.13.0",
  "answers": {
    "variant_hero": {
      "type": "choice",
      "choice": "specTable",
      "probabilities": { "bigImage": 0.12, "specTable": 0.88 },
      "confidence": 0.81
    },
    "presence_financing": { "type": "noul", "noul": 0.22 },
    "intensity_urgency": {
      "type": "score",
      "score": 0.35,
      "probabilities": { "0": 0.7, "1": 0.25, "2": 0.05 },
      "legend": { "0": "none", "1": "soft", "2": "urgent" },
      "confidence": 0.62
    }
  },
  "usage": { "input_tokens": 296, "output_tokens": 20 }
}
Two details that trip people up. A Noul returns a probability, not a boolean: 0.22 means probably not. A Score returns a float that is the probability-weighted mean of the level indices, not a level name: 0.35 sits between “none” and “soft”, nearer none. Different distributions can produce the same float, so read probabilities alongside it. Ordering sorts on that float directly, which is finer grained than an index and makes ties rare.

Twelve questions cost about what one costs

Questions in a single request are evaluated in parallel, so adding more has little effect on wall clock. That changes how you design: rather than asking a broad question and branching on the answer, you ask every narrow question up front, including ones that will turn out to be irrelevant, and throw away the answers you do not need in code.

The prototype asks twelve questions on every uncached request. Several are about panels that may end up hidden. That is deliberate, and it is cheaper than the round trip it saves.

Latency, honestly

TypeSafe documents a typical query at about 100 ms. The prototype’s two live measurements, from a residential connection to the public endpoint, were 724 ms and 468 ms end to end for twelve questions. Assembly and rendering together are hundredths of a millisecond, so essentially all of it is the round trip.

Both numbers miss the prototype’s own 300 ms target. They are reported here rather than rounded away because a framework whose pitch is speed should publish the number that embarrasses it. Plan for the half-second, cache aggressively on the state fields your spec actually reads, and treat a repeat visitor as free.

Where the key lives

The API key is read from the server environment and never reaches the browser. The decide call happens in a route handler or server action; the client receives a Decision, not a token. An upstream error body is redacted before it is ever surfaced, because a gateway that echoes request headers into an error response is not exotic.
